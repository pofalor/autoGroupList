# Архитектура системы управления задачами и рабочим временем

## Общее описание
Система предназначена для помощи  старосте в учёте посещаемости.

## Рабочее пространство (Workspace)

### Типы рабочих пространств
- **Личное рабочее пространство**:
  - У каждого пользователя может быть только **одно** личное рабочее пространство
  
- **Корпоративное рабочее пространство**:
  - Должно иметь **уникальное имя** в рамках одного управляющего (создателя)
  - Запрещены дубли:
    - ИНН организации
    - Комбинация: **дата регистрации + юридический адрес + страна**

## Информация о рабочем пространстве (Projects)

### Основные разделы
1. **Проекты**:
   - Список проектов в выбранном рабочем пространстве
   
2. **Приглашения**:
   - Управляющий может:
     - Приглашать пользователей по **email** или **никнейму** (поиск только по полному совпадению)
     - Удалять пользователей из организации
   - Пользователи:
     - Видят приглашения (как отправленные им, так и полученные)
     - Могут принимать или отклонять их
     - Не могут получать новые приглашения, пока не обработают текущее
   - Ограничения:
     - Приглашения **нельзя изменить или удалить** после отправки
     - Видны только **ожидающие приглашения**

## Техническая реализация

### Сущности и процессы
- **`UserWorkspaceStatusChange`**:
  - Создается при отправке приглашения
  - При принятии (`IsConfirmed = true`):
    - Создается `WorkspaceMember`
  - При отклонении:
    - `WorkspaceMember` не создается
  - При удалении пользователя:
    - Создается новая `UserWorkspaceStatusChange`
    - `WorkspaceMember` помечается статусом `"Deleted"`

- **Создание рабочего пространства**:
  - Автоматически создается `WorkspaceMember` для создателя с ролью `Owner`

## Новый функционал

### 1. Автоматическое списывание часов
- Добавляется **кнопка** для автоматического трекинга времени

### 2. Администрирование компаний
- **Администратор** проверяет и подтверждает новые компании:
  - **Личные** рабочие пространства не требуют подтверждения
  - **Корпоративные** требуют обязательного подтверждения
- **Правила подтверждения**:
  - Администратор не может подтвердить собственное рабочее пространство. Подтверждение должно выполняться другим администратором
- **Правила отображения**:
  - Создатель видит статус (`Pending`, `Approved`, `Rejected`)
  - Остальные пользователи **не видят** пространство до подтверждения
  - Неподтвержденные пространства видны только:
    - Создателю пространства
    - Администраторам системы

### 3. Отчёты
- Функционал в разработке (не срочно)

### 4. Удаление из рабочего пространства
- При удалении пользователя **автоматически останавливается** трекинг его задач

Как будет проходить workflow в отмечающем тг боте: 
1. Есть расписание, хранящее ссылку на предмет. 
2. Когда юзеров надо уведомить, что они отмечены на занятии, будет создаваться нотификашн, который будет ссылаться на расписание. 
3. Юзеров уведомили, им кнопка отправилась. Дальше они на кнопку жмут, кнопка скрывается. Если сегодня есть такое занятие, отмечаем его (создаём запись в Attendance), если нет, показываем ошибку и скрываем кнопку.
4. В конце дня или по запросу старосты отправляем ему список Attendance за сегодня. В конце дня если отправили, то отправляется через нотификашн, если не в конце дня, то просто на лету отправляем. 

При масштабировании до ВУЗовского уровня: 
1. Добавить механизм подгрупп и настройки делится ли группа на подгруппы. 

Дальнейшие фичи: 
1. Нужно добавить задание списка группы через команду, которая доступна только старосте (как с командой расписания). Формат списка группы (формат старосте должен будет показываться, чтобы он понимал в каком формате отправлять данные): 
1. Иванов Иван Иванович 
2. Иванов Илья Юрьевич
...  

При изменении списка группы, сущности, связанные со Student, должны переезжать в архив (как происходит при изменении расписания).

## Работа в двух мессенджерах

Бот отвечает и в телеграме, и во ВКонтакте. Отмечаться можно в любом из них, привязать можно оба.

Слои:

1. **Транспорт** — `GroupListNet.Core/src/Bot/IMessengerClient.cs` и его реализации
   `TelegramMessengerClient` и `VkMessengerClient`. Знают только про отправку, изменение сообщения,
   снятие кнопок и ответ на нажатие. Все различия API мессенджеров закрыты здесь.
2. **Логика команд** — `GroupListNet.Core/src/Bot/BotUpdateHandler.cs`. Общая для всех мессенджеров,
   транспорт приходит параметром, поэтому ответ всегда уходит туда, откуда пришло сообщение.
   Модели `BotMessage`, `BotCallback`, `BotKeyboard` не зависят от мессенджера.
3. **Приём обновлений** — `TelegramBotBackgroundJob` (long polling телеграма) и `VkBotBackgroundJob`
   (Bots Long Poll ВКонтакте). Обе задачи только переводят обновления в общие модели и зовут обработчик.
   Задача не запускается, если её мессенджер не настроен в конфиге.
4. **Отправка уведомлений** — общий `NotificationSenderBackgroundJob` проходит по всем настроенным
   мессенджерам и забирает неотправленные уведомления своего канала.

Личность студента: `Student.TelegramId` и `Student.VkId`, оба необязательные. `null` означает,
что мессенджер не привязан — на это опираются выборки незарегистрированных студентов.
Регистрация идёт по номеру в списке группы отдельно в каждом мессенджере, поэтому студент,
зарегистрированный в телеграме, может позже привязать и ВКонтакте — это будет та же запись Student.

Уведомления: у `Notification` есть поле `Messenger`. Студенту с двумя привязками
`StudentScheduleBackgroundJob` создаёт по уведомлению на каждый мессенджер, и кнопка «Я на паре»
приходит в оба. Отметка при этом засчитывается один раз: `MarkAttendanceAsync` обновляет
существующую запись, а на повторное нажатие бот отвечает, что студент уже отмечен.

Текст сообщения в базе не хранится. В таблице лежит только сам факт уведомления — тип, мессенджер,
адресат, ссылка на занятие, статус доставки и текст ошибки, — а содержимое собирает
`GroupListNet.Core/src/Bot/NotificationMessageBuilder.cs` в момент отправки: напоминание о паре —
из расписания и предмета, отчёт старосты — тем же `LeaderListFormatter`, что отвечает на `/list`.

Сборка при отправке безопасна благодаря мягкому удалению: `Schedule`, `Subject`, `Attendance`
и `Student` только помечаются `IsDeleted`, глобальных фильтров в `ApplicationDbContext` нет,
поэтому `Include` видит и архивные строки. Отчёт за прошедший день берёт отметки
`IAttendanceRepository.GetAttendanceForReportAsync` — это отдельный метод без условия на
`IsDeleted`, чтобы перезаливка расписания или списка группы между созданием отчёта и его
отправкой не превратила его в «никто не отметился». Обычный `GetTodayAttendanceAsync`, которым
пользуются `/list` и перенос отметок на сайт, архив по-прежнему не показывает.

Ограничения ВКонтакте, которые учитывает `VkKeyboardBuilder`:

- под сообщением помещается не больше шести кнопок, поэтому длинные списки студентов
  (`/add_leader`, `/remove_leader`, `/attend_other_group`) показываются обычной одноразовой
  клавиатурой — не больше десяти рядов по пять кнопок;
- подпись кнопки обрезается до 40 символов, всплывающий ответ — до 90;
- разметки нет, символы markdown из текста убираются;
- изменить только клавиатуру нельзя, нужен текст сообщения. Текст сообщения с кнопкой ВКонтакте
  в событии не присылает, поэтому там кнопка иногда остаётся — обработчик рассчитан на повторное нажатие.
